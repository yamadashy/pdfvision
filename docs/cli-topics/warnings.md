# Warnings and raw density signals reference

`pages[].warnings[]` carries page anomalies that deserve visual attention, and the density Overview carries the raw per-page signals that feed `quality`. JSON-style paths here are exact for JSON, decoded TOON, and `processDocument()`; XML uses the mappings in `pdfvision docs formats`. `pdfvision docs schema` carries the `quality.nativeTextStatus` / `quality.visualStatus` field summary; this topic is the lookup companion for **what each raw signal means** and **what to do when a specific warning code fires** beyond the self-explanatory inline `warning.message`.

Read this only when a `warnings[]` code needs interpretation past its inline message, or when you want the raw signal thresholds behind a `quality` status.

The machine-readable side of this — the `PageWarning` TypeScript interface (`code` union, `severity`, `message`, `blockIndex` / `otherBlockIndex` / `imageBoxIndex` / `tableIndex`), the exact firing conditions, and which flag each code requires — is the `## Shape` section directly below.

pdfvision deliberately stops at observation: it does **not** recommend an action. The action is the agent's call based on the two `quality` statuses plus the raw signals below. Silent failures — empty `text` that looks fine to a downstream consumer, or full `text` that is actually NUL bytes — become visible up front; that is the reason to prefer pdfvision over reading a PDF directly.

## Shape

```ts
interface PageWarning {
  code:
    | 'text_overlap'
    | 'near_bottom_edge'
    | 'body_near_repeated_chrome'
    | 'page_edge_text_truncated'
    | 'off_page'
    | 'glyph_garbage_text'
    | 'rtl_script_text'
    | 'localized_glyph_noise'
    | 'font_mapping_warning'
    | 'symbol_font_substitution'
    | 'raw_embedded_source_text'
    | 'invisible_text'
    | 'text_under_opaque_fill'
    | 'text_matches_background'
    | 'dense_vector_graphics'
    | 'vector_graphics_no_native_text'
    | 'text_row_vector_bars'
    | 'duplicate_text_layer'
    | 'raster_image_no_native_text'
    | 'tabular_numeric_layout'
    | 'vector_chart_labels'
    | 'layout_table_uncertain'
    | 'dot_leader_noise'
    | 'tiny_native_text_noise'
    | 'raster_backed_text_layer'
    | 'raster_text_layer_symbol_noise'
    | 'raster_text_layer_word_fragmentation'
    | 'ocr_low_confidence'
    | 'ocr_native_text_mismatch'
    | 'ocr_native_spacing_loss'
    | 'large_raster_low_text_overlap'
    | 'annotation_text_missing_from_native'
    | 'optional_content_text_may_include_hidden_layers'
    | 'reading_order_divergence'
    | 'rotated_page_read_unrotated'
    | 'xfa_form'
    | 'xfa_fields_only'
    | 'xfa_static_content';
  severity: 'warning' | 'error';
  message: string;
  blockIndex?: number;        // 0-based into pages[N].layout.blocks
  otherBlockIndex?: number;   // for pair-wise rules (text_overlap, body_near_repeated_chrome)
  imageBoxIndex?: number;     // 0-based into pages[N].imageBoxes for image-region rules
  tableIndex?: number;        // 0-based into pages[N].layout.tables for layout_table_uncertain
}
```

`pages[].warnings[]` is omitted when no rule fired. Geometry warnings require `--layout` because they pin to layout blocks, and are suppressed on heavily glyph-corrupted pages where native bboxes are not trustworthy. Image-region warnings can use pdfvision's internal image-box pass even when `--image-boxes` was not requested; `imageBoxIndex` is emitted only when public `pages[].imageBoxes` exists. `large_raster_low_text_overlap` gets stronger overlap evidence when `--image-boxes` is combined with `--layout` or `--geometry`, because it can compare image boxes against native text bboxes. It is not emitted on empty-native-text pages where `raster_image_no_native_text` already fired. `tabular_numeric_layout` and `vector_chart_labels` require `--layout` because they inspect layout lines and blocks. `tiny_native_text_noise` requires `--layout` or `--geometry` because it inspects font-size geometry. `duplicate_text_layer` uses internal spans and can appear without `--layout` or `--geometry`; it may co-occur with `off_page` or `text_overlap` because those are separate geometry symptoms of the inflated native layer. `annotation_text_missing_from_native` can use pdfvision's internal annotation pass even when `--annotations` was not requested; public `pages[].annotations` is still emitted only with `--annotations`. `glyph_garbage_text`, `rtl_script_text`, `localized_glyph_noise`, `font_mapping_warning`, `symbol_font_substitution`, `raw_embedded_source_text`, `invisible_text`, `text_under_opaque_fill`, `text_matches_background`, `dense_vector_graphics`, `vector_graphics_no_native_text`, `dot_leader_noise`, and `optional_content_text_may_include_hidden_layers` use always-on page/document signals and can appear without layout. `invisible_text`, `text_under_opaque_fill`, and `text_matches_background` reuse the page operator list already fetched for image/vector analysis and are suppressed on raster-backed OCR text layers; annotation appearance operators, complex path geometry, transparent, clipped, soft-masked, transparency-group, or optional-content fills, and non-normal blend-mode fills are excluded from opaque-fill evidence. `dense_vector_graphics` can also use internal vector-box geometry to suppress text-dominant pages whose dense vectors are only small scattered decorations. `raster_backed_text_layer`, `raster_text_layer_symbol_noise`, `raster_text_layer_word_fragmentation`, and `raster_image_no_native_text` use the internal image-box pass and can appear even when `--image-boxes` was not requested. `ocr_low_confidence`, `ocr_native_text_mismatch`, and `ocr_native_spacing_loss` require `--ocr`. `xfa_form`, `xfa_fields_only`, and `xfa_static_content` are the document-level always-on XFA signals, attached to the first extracted page and describing the whole selection rather than that page; exactly one of them fires on a document that declares XFA, decided from what the extracted pages actually contain. `xfa_form` carries the verdict in its severity — `error` when the placeholder is confirmed, `warning` when it is only unconfirmed.

The current rule catalog:

- `text_overlap` — non-repeated layout blocks overlap in a way that may scramble reading order. Shallow adjacent-line bbox slack from inline math, multi-line math annotations, superscripts, subscripts, punctuation-only inline fragments, dotted map/decorative texture blocks, and callout-marker continuation lines is suppressed.
- `near_bottom_edge` — body text ends unusually close to the page bottom.
- `body_near_repeated_chrome` — body text overlaps or nearly touches detected repeated header/footer chrome.
- `page_edge_text_truncated` — an extracted run of at least 8 code points and 6em reaches or crosses the page boundary by at most 1.25em along its primary writing axis, matching the last-kept-glyph signature when pdf.js drops later glyphs outside the page box. Natural punctuation endings are suppressed. Always-on through internal span geometry; `blockIndex` is included when layout is available, and a same-block `off_page` finding is suppressed in favor of this content-loss warning.
- `off_page` — a layout block bbox extends beyond the page.
- `glyph_garbage_text` — `quality.nativeTextStatus` is `mixed_glyph_indices` or `unusable_glyph_indices`, or native text is dominated by Private Use Area glyph-code strings; native text is partly or mostly raw glyph-index garbage and should be checked against render/OCR before use.
- `rtl_script_text` — at least 50 Unicode letters are present and more than 25% fall in Hebrew, Arabic, or related strong right-to-left ranges; logical order is preserved, but inter-word spaces may disappear and paired brackets may be mirrored, so compare against the render when exact wording matters.
- `localized_glyph_noise` — multiple non-printable code points appear below the mixed-glyph threshold, Unicode replacement characters (`U+FFFD`) appear in otherwise usable native text, private-use glyph codes dominate a short run or repeat throughout otherwise readable text, isolated Latin-extended mojibake appears inside CJK text, adjacent Latin-1 supplement printable mojibake dominates a short text run, many adjacent CJK glyphs are separated by likely artificial spaces or duplicated as adjacent pairs, or printable font-map noise puts uppercase `LJ` inside an otherwise lowercase word such as `veriLJcation`; often broken formulas, comparison symbols, unit marks, bullets, dotted leaders, non-Latin custom fonts, icon-font symbols, CJK text-positioning artifacts, text-layer duplication, or ligature/font-map substitutions.
- `font_mapping_warning` — pdf.js reported missing or suspicious font character-map data while native text otherwise looked usable; visible text may render correctly but extract as printable glyph substitutions, so compare against the render when exact text matters.
- `symbol_font_substitution` — one font on the page is used only for single glyphs set inline at body size directly beside a number in another font (`.001` without its leading zero counts), and at least two of those glyphs extract as a digit or a Latin-1 letter (`2`, `þ`, `ð`); commas, periods, and fractions (`,`, `.`, `¼`) beside numbers are reported alongside once the font qualifies, but never qualify it on their own, because TeX sets the decimal points and commas of math-mode numbers from its math-italic font and those really are punctuation. That is the shape of a separate symbol font whose character map reports minus, `<`, `>`, `±`, or `=` as ordinary characters: `−52%` extracts as `252%`, `<0.001` as `,0.001`, `7.1 ± 0.9` as `7.1 þ 0.9`. The message names the font alias (the `fontName` in `--geometry` spans), the extracted characters, samples in context, and a `--render-region` covering the runs set beside numbers (clipped to the page); the font's other short runs, such as a sign between two variables, may be wrong too and are not in it. Signs and comparison operators in that text are not trustworthy; read them from the render. Fonts that set only punctuation or fractions beside numbers, raised or smaller superscripts, fonts that also set longer runs, and pages positioned glyph by glyph do not fire it. A document whose only mis-mapped sign is `<` read as `,` is therefore not flagged.
- `raw_embedded_source_text` — long embedded producer/source payloads such as `<latexit...>` LaTeX image source leaked into native text; treat matching `pages[].text`, layout text, and search hits as machine residue until checked against render/OCR.
- `invisible_text` — one or more text-show operations ran while PDF text rendering mode `Tr 3` was active. pdf.js exposes the mode change and decoded glyph Unicode in the page operator list, so the warning includes a short sample when available. The text remains in `pages[].text` but is not painted for a human viewer; compare against `--render` before trusting it. Suppressed when a full-page raster indicates an OCR text layer, including sparse OCR residue below the normal `raster_backed_text_layer` threshold. Text drawn in the colour of its background is `text_matches_background`.
- `text_under_opaque_fill` — native text of at least 3 non-whitespace characters is hidden by a later-drawn rectangular path fill with alpha from 0.9 through 1, dark luminance at most 0.2, normal blend mode, and no active clip, soft mask, transparency group, or optional-content frame. Coverage is decided **per glyph** wherever the operator list lets pdfvision place each glyph (it replays the text matrix, `Td`/`TJ` offsets, character/word spacing, horizontal scaling, rise, and the font matrix the way pdf.js paints them): a glyph is hidden when the fill covers at least 90% of its body (the middle of its advance, from just above the baseline to about x-height), so a box over a few words inside a sentence is found. Consecutive hidden glyphs on one line form a passage; a glyph that later text is painted on top of (a white label over a dark bar) is not hidden. The warning lists up to three passages as `"text" (bbox x,y,w,h)` in raw page units, ready for `--render-region`, plus a count; when there are more it adds the bbox enclosing all of them. Runs whose glyphs cannot be placed (vertical writing, negative font size, missing advance widths) fall back to whole-span coverage of at least 90%, which reports the span text and bbox. For that fallback, detection aligns normalized spans from the end against ordered operator-list text-show runs; one span may match an exact deterministic concatenation of adjacent runs, and only fills painted after the last ordered exact match qualify. This prevents a deduplicated span from being treated as hidden when identical foreground text was repainted after the fill. Collection and matching fail closed when page evidence exceeds 4,096 candidate spans, text runs, or candidate fills; 65,536 span, raw-run, or NFKC-normalized UTF-16 code units; 1,000,000 run/code-unit comparison steps; or 250,000 span/fill coverage checks; the glyph path fails closed above 2,000,000 glyph/fill and glyph/glyph comparisons. The path data itself must prove a single closed axis-aligned rectangle under an axis-preserving CTM. Complex paths (including holes and disconnected subpaths), annotation appearance operators, strokes, light/translucent/transparent, clipped, soft-masked, transparency-group, or optional-content fills, non-normal or unparseable blend-mode fills, underlines and strike-through rules (they cover too little of a glyph's body), boxes over fewer than 3 characters, fills painted before foreground text, rotated or skewed path boxes, invalid geometry, and unparseable colors are ignored. CTM, fill color/transparency, nonstroking alpha, blend mode, clip, soft-mask, and marked-content state are tracked through save/restore and Form XObjects. Form BBox clips are treated as active clips. Detection is suppressed on raster-backed OCR text layers. No `--geometry`, `--vector-boxes`, or `--annotations` flag is required, and the warning does not change `quality`.
- `text_matches_background` — native glyphs (fill rendering modes `Tr 0`/`Tr 4`) whose fill colour, after compositing with the nonstroking alpha, is within 8/255 per RGB channel of the paint behind them — white text on a white page, blue text on a box of the same blue, or text at alpha 0. Glyphs are placed as for `text_under_opaque_fill`. The colour behind a glyph is known only when the most recent paint overlapping the glyph's body is an opaque, unclipped, axis-aligned rectangle of a device colour that contains it, or when nothing was painted there (viewers render the page white). Any other paint under the glyph — complex or rounded paths, pattern or gradient fills, shadings, translucent, clipped, transparency-group, or optional-content fills, strokes — makes the background unknown and the glyph is not reported; so does any raster image overlapping the glyph, a later visible glyph painted on top of it (halo or knockout copies), a glyph off the page, text under a soft mask or a non-normal blend mode, stroke-only and invisible rendering modes (`Tr 3` is `invisible_text`), and pattern-filled text. Severity is `warning`, not `error`: the extraction is faithful to the file, and the commonest real cause is invisible production metadata (for example the GPO "VerDate … Jkt …" slug on every Federal Register page) rather than concealment. The warning lists up to three passages of at least 3 non-whitespace characters as `"text" (bbox x,y,w,h)` in raw page units, plus a count and, when there are more, the bbox enclosing all of them. Paint history fails closed above 4,096 recorded paints or 2,000,000 background checks. Suppressed on raster-backed OCR text layers; no flag is required, and the warning does not change `quality`.
- `text_row_vector_bars` — at least four same-height coloured bars stacked in text rows, with no text inside them and varying in start and length (a Gantt schedule) or in length from one start (a bar chart): the text has the row labels, not the dates, durations, values or status the bars show. The message names a region (the rows, plus the scale or legend just above and below) to `--render-region`.
- `dense_vector_graphics` — the page contains many meaningful vector drawing operations; often form boxes, table rules, chart paths, checkboxes, or diagrams whose visible structure is not represented by native text. Text-dominant pages whose many vectors are only small scattered decorations are suppressed when vector-box geometry is available.
- `vector_graphics_no_native_text` — a nonblank vector-only page has no native text; symbols, diagrams, or path-drawn labels can be visible in the render but absent from `pages[].text`.
- `tabular_numeric_layout` — many short numeric lines form multiple aligned columns with shared row positions; often financial statements or dense numeric tables whose row/column relationships are visually obvious but can be flattened in plain native text. Chart-axis tick labels and irregular chart data-label rows are suppressed.
- `vector_chart_labels` — a vector chart's labels (values, legend, categories) were kept together in the body, but which value belongs to which bar or series is only in the drawing.
- `layout_table_uncertain` — a `layout.tables[]` hint did not resolve into one consistent grid, so some of its cells may sit in the wrong row or column, or be missing. `tableIndex` names the table and the message carries its bbox as a ready `--render-region`.
- `dot_leader_noise` — many standalone dotted leader/noise lines were extracted as separate layout text; often table-of-contents leaders, table leaders, map stipple, or decorative dot patterns that visually connect labels or represent texture but can appear as noisy dot paragraphs in plain native text.
- `tiny_native_text_noise` — one or more long native text runs are set at extremely small sizes, often hidden producer links or machine-readable residue. Treat matching `pages[].text`, links, and search hits as possibly not human-visible until checked against the render. Requires `--layout` or `--geometry`.
- `duplicate_text_layer` — native text contains a hidden near-duplicate layer of visible content at a consistent scaled/shifted position, so `pages[].text` is inflated and layout blocks may merge duplicate runs; prefer the render or OCR when exact visible text matters. It may co-occur with `off_page` or `text_overlap`, which remain separate layout-geometry signals.
- `raster_backed_text_layer` — native text appears to be an OCR/text layer over a full-page raster image, including sparse OCR layers on scanned covers with minor decorative vector marks; text may be useful but error-prone, and bbox/layout geometry can drift from the pixels a human sees.
- `raster_text_layer_symbol_noise` — a raster-backed native text layer is dominated by printable punctuation/symbol noise; common on old scan OCR title pages where `quality.nativeTextStatus` can still be `ok` even though the native text is visibly unreliable.
- `raster_text_layer_word_fragmentation` — a raster-backed native text layer contains many isolated Latin-letter fragments, a common old-OCR failure where words like `report` extract as `r e p o r t`; exact wording and native search misses should be checked against `--ocr` or the render.
- `raster_image_no_native_text` — a raster image dominates the page while native text is empty, so human-visible text inside the image will not appear in `pages[].text`; compare the render or OCR when exact text matters. On empty-native-text pages this warning subsumes `large_raster_low_text_overlap`.
- `ocr_low_confidence` — `--ocr` ran with confidence below 0.5 while native extraction was empty, sparse, glyph-corrupted, or attached to a raster-backed text layer; OCR text is present but should be treated as tentative until checked against the render, language choice, or a focused crop.
- `ocr_native_text_mismatch` — `--ocr` ran with high confidence and short OCR text of comparable length strongly disagrees with otherwise-ok native text; often a custom font that renders a word correctly while extracting as printable glyph substitutions.
- `ocr_native_spacing_loss` — `--ocr` ran on a raster-backed text layer with high confidence, OCR and native text contain comparable characters, but native text has lost many word boundaries; often scan OCR layers that extract as glued words even though OCR restores normal spacing.
- `large_raster_low_text_overlap` — a large raster image dominates a page whose native text is empty or sparse, or bbox-enabled extraction found little overlapping native text, so labels, chart text, map text, or screenshot text inside it will not appear in native text. The message ends with the next step: `--render-region` for the image's region (clipped to the page), or `--ocr`. It is not emitted on empty-native-text pages where `raster_image_no_native_text` already fired.
- `annotation_text_missing_from_native` — one or more visible FreeText annotation appearances have `contents` that are not represented in `pages[].text`; read `pages[].annotations` or use `--search` / `--render-region` before treating native text as complete. Can appear even when `--annotations` was not requested for output.
- `optional_content_text_may_include_hidden_layers` — the page text stream contains optional-content marked text while the PDF has at least one default-hidden layer; `pages[].text` may include layer content that the initial viewer render does not show, so inspect `--layers` and compare against `--render`.
- `reading_order_divergence` — visual reading order differs from `pages[].text`. This fires when a heading that leads `layout.blocks` only appears in the back half of the native text stream, when a slide-style visually-first title/header is drawn last and appears at the end of native text, when a late bottom note or right sidebar appears at the start of native text, when reconstructed layout lines inside one block are emitted out of order, when a compact math-like block appears with reordered characters such as a superscript emitted after the baseline expression, or when `--form-fields` exposes form labels whose native text order differs from the visible row order; form date placeholders such as `MM / DD / YYYY` are suppressed. Prefer `layout.blocks` order over `pages[].text` when sequence matters — the Markdown formatter already rebuilds the body from layout blocks on these pages. When the layout order is itself broken — side-by-side prose blocks alternating line by line (at least four switches, each side resuming within one line of leading), or one block whose prose lines share no horizontal extent because it ran on into the next column — the message instead says `the layout-rebuilt order is unreliable here too`, names the blocks, and ends `render the page to read it in sequence`. Requires `--layout`; `blockIndex` points at the displaced heading, slide title/header, late block, local block, or form-label block.
- `rotated_page_read_unrotated` — the page is stored with `/Rotate` 90, 180, or 270, but its text is upright only in the stored orientation, so a viewer would show it sideways or upside down. pdfvision reads, reports, and renders that page unrotated instead of in the displayed frame every other page uses: bboxes, `width` / `height`, `--render-region`, and `--render` all follow the stored page. Text set the other way (upright only as displayed) reads sideways in that frame: when it is at least 5% of the characters, the message gives its share and says to render the page and read that text from the image. Otherwise nothing to recover; it explains why this page's size and render are not turned by its `rotation`.
- `xfa_form` — document-level. Severity `error`: the PDF declares an XFA (LiveCycle) form **and** the extracted pages are confirmed to be only the viewer placeholder ("Please wait..."). The real form content is not extracted, so nothing here is evidence about the form — do not answer from it, and do not expect a render to help. Severity `warning`: XFA is declared and nothing extracted looks like content, but no marker confirmed the placeholder either — render or OCR the pages to settle it. Attached to the first extracted page, true of the whole selection. JSON/TOON/library use top-level `xfa: true`; XML uses `<document xfa="true">`.
- `xfa_fields_only` — document-level: the PDF declares an XFA (LiveCycle) form whose static AcroForm field layer is real and was extracted, while the pages carrying it hold nothing of their own — the viewer placeholder, or nothing at all. The fields are evidence; the page text is not. Attached to the first extracted page, true of the whole selection.
- `xfa_static_content` — document-level: the PDF declares an XFA (LiveCycle) form and the extracted pages are the document's own content rather than a viewer placeholder — the hybrid AcroForm+XFA shape most government forms use, or any XFA file whose pages carry text, images, or vector drawing of their own. Read them as usual, with the other page warnings saying what each is worth; only values held solely in the XFA layer are missing. Attached to the first extracted page, and carries the same top-level `xfa: true` / `<document xfa="true">`.

Same observational posture as `quality`: pdfvision tells the agent what it saw; the agent decides whether to surface, re-OCR, or zoom in via `--render-region`.

## The density Overview

When `result.pages.length > 1`, markdown output starts with an Overview table: `Chars / Images / Coverage / Size` per page, plus `Rotation` (when any page is rotated), `Vectors` (any page with vector drawing operations), `NonPrint` (any page with non-zero non-printable ratio), `Tables` (`--layout` found row-major table hints), and `Blocks` (`--layout` was on). With `--layout`, markdown also renders detected `layout.tables[]` as per-page `Layout tables` sections so financial statements and other numeric tables keep row/value relationships in chat-readable output.

JSON, decoded TOON, and `processDocument()` carry these signals in `overview[]` as `charCount` / `imageCount` / `vectorCount` / `textCoverage` / `nonPrintableRatio` / `nonPrintableCount` / `rotation` / `width` / `height` / nested `quality`. XML uses `<overview><page no="..." ...>` attributes, flattens `quality` into `nativeTextStatus` / `visualStatus`, and currently omits overview rotation. Read the Overview before scrolling the body.

## Raw signals (the inputs to `quality`)

- `textCoverage: 0` (rendered as `coverage: 0%` in markdown) + `imageCount > 0` → the page body is a rasterised image. The text stream is empty. Re-run with `--ocr` or `--render`.
- Very low `textCoverage` plus `imageCount > 0` / `vectorCount > 0` and only a few characters → the visible page is mostly outside native text (`quality.nativeTextStatus === 'sparse_text_with_visual_content'`). Render before trusting the sparse text.
- Very low `charCount` plus dense vector structure can also map to `sparse_text_with_visual_content` even when `textCoverage` is not low, because one large watermark text item can cover much of the page while the visible form/table/chart content lives in vectors.
- Any native text plus `quality.visualStatus === 'blank'` → the native text is not visible in the rendered page (`quality.nativeTextStatus === 'sparse_text_on_blank_visual'`). Common in scanned-book front matter, invisible/broken-font text, and failed renders; do not treat the text as the human-visible page content.
- `vectorCount > 0` with low text coverage → visible non-raster structure exists (forms, chart paths, slide shapes, diagrams) even when `imageCount` is zero. Inspect with `--render` when the visual layout matters.
- `nonPrintableRatio >= 0.05` → pdf.js fell back to raw glyph indices for at least part of the page because some fonts lack a ToUnicode CMap (common with Hebrew, older CJK, custom symbol fonts, and branded annual reports). `0.05–0.3` maps to `quality.nativeTextStatus === 'mixed_glyph_indices'`: some text may be readable, but native extraction is incomplete. `>= 0.3` maps to `unusable_glyph_indices`: treat the native text as mostly garbage. The raw count is in `nonPrintableCount` — when the 3dp ratio rounds to 0 the count still tells you whether any non-printable code points slipped through (useful for "is there ANY garbage in this page?" filters). Normalized `pages[].text` strips non-visible C0 controls other than tab / newline / carriage return, but these counters still use the pre-strip text signal so sparse control-byte evidence remains visible.
- `charCount: 0` but `imageCount: 0` → genuinely blank page (separator, end matter).
- Sudden drop in `textCoverage` on a single page in an otherwise text-dense doc → that page is likely a figure / scan / chart. Inspect with `--render`.
- `quality.visualStatus === 'sparse'` → the rasterised page is not blank, but the visible marks are too small/sparse to call the page visually populated. This can be a one-line text-only page as well as a tiny image/vector/annotation mark. Use object geometry (`spans`, `vectorBoxes`, `imageBoxes`, `annotations`, `visualRegions`) or `--render-region` to inspect the mark instead of treating this as a render failure.
- `quality.visualStatus === 'blank'` → the rasterised page came out blank **against its own dominant background**. Likely a render-pipeline failure (pdf.js + @napi-rs/canvas can't decode JPEG2000 image streams, or the font has no resolvable glyphs) or a genuinely blank page. The ratio is background-aware — dark book covers and beige scan paper don't false-trip it. OCR on this page returns `confidence: 0` not because OCR failed but because the input was a near-uniform image.

## Warning catalog (agent action per code)

Flag requirements per code are noted inline. Geometry warnings pin to layout blocks, so they require `--layout`; several text-quality and image warnings ride on always-on or internal passes and appear even without the matching output flag. See `## Shape` above for the precise firing/suppression conditions.

- **`text_overlap`** (needs `--layout`) — non-repeated layout blocks overlap in a way that may scramble reading order. Prefer `layout.blocks` order; render the region when sequence matters.
- **`near_bottom_edge`** (needs `--layout`) — body text ends unusually close to the page bottom.
- **`body_near_repeated_chrome`** (needs `--layout`) — body text overlaps or nearly touches detected repeated header/footer chrome.
- **`page_edge_text_truncated`** (always-on text-geometry signal) — a long extracted text run reaches or slightly crosses the page boundary along its writing axis, matching pdf.js's signature when later glyphs were dropped outside the page box. Native text may be incomplete; inspect `--render` or `--render-region` to see what the page actually shows. Natural punctuation advance at a flush edge is suppressed.
- **`off_page`** (needs `--layout`) — a layout block bbox extends beyond the page.
- **`glyph_garbage_text`** (always-on text-quality signal) — fires when `quality.nativeTextStatus` is `mixed_glyph_indices` or `unusable_glyph_indices`, or when native text is dominated by Private Use Area glyph-code strings even though `nonPrintableRatio` is 0. Treat native `text`, `spans`, search hits, and layout text as incomplete or unreliable; inspect `--render` and consider `--ocr`.
- **`rtl_script_text`** (always-on text-quality signal) — fires when a page has at least 50 Unicode letters and more than 25% of them are in Hebrew, Arabic, or related strong right-to-left ranges. Native extraction remains in logical order, but inter-word spaces can disappear and paired brackets can be mirrored; compare against `--render` when exact wording matters.
- **`localized_glyph_noise`** (always-on text-quality signal) — fires when multiple non-printable code points appear below the mixed-glyph ratio threshold, when native text contains Unicode replacement characters (`U+FFFD`), when private-use glyph codes dominate a short run, when a CJK page contains isolated Latin-extended mojibake characters, when text is dominated by Latin-1 supplement printable mojibake, when many adjacent CJK glyphs are separated by likely artificial spaces or duplicated as adjacent pairs, or when printable font-map noise puts uppercase `LJ` inside an otherwise lowercase word such as `veriLJcation`. Common cases: formulas, comparison symbols, unit marks, bullet symbols, dotted leaders, non-Latin custom fonts, icon fonts, CJK text-positioning artifacts, text-layer duplication, or ligature/font-map substitutions that render fine but extract as control characters, replacement glyphs, artificial spaces, duplicated CJK glyphs, or stray printable glyphs.
- **`font_mapping_warning`** (captured pdf.js font/CMap warnings) — fires when native text otherwise looks `ok` but pdf.js reported missing character-map data. Common case: a custom embedded font renders visibly but extracts as printable glyph substitutions; inspect `--render` when exact text matters.
- **`symbol_font_substitution`** (internal spans; no flag required) — fires when one font is used only for single glyphs set inline beside numbers in another font, and at least two of them extract as digits or Latin-1 letters (punctuation and fractions alone never fire it). Common case: journal PDFs that take minus, `<`, `>`, `±`, and `=` from a symbol font with a wrong character map, so `−52%` reads as `252%` and `p < 0.001` as `p , 0.001`. The PDF itself states the wrong characters, so pdfvision cannot correct them; render the region the message names and read signs and comparison operators from the image before reporting a direction, a bound, or a p-value.
- **`raw_embedded_source_text`** (always-on text-quality signal) — fires when long embedded producer/source payloads such as `<latexit...>` LaTeX image source leak into native text. Treat matching `pages[].text`, layout text, and search hits as machine residue until checked against `--render` or `--ocr`.
- **`invisible_text`** (always-on operator-list signal) — the page contains text drawn with PDF rendering mode `Tr 3`: it is included in native extraction but a human viewer cannot see it. This is an error-level trust signal; treat the sampled text and matching native search hits as unverified until compared with `--render`. Full-page raster/OCR text layers are suppressed because invisible text is expected there and the existing scan warnings already explain that trust boundary, including sparse OCR residue below the normal `raster_backed_text_layer` threshold. Text drawn in the colour of its background (for example white on white) is reported separately as `text_matches_background`.
- **`text_under_opaque_fill`** (always-on operator-list signal) — native text remains extractable even though a later opaque dark rectangular path fill hides it. Coverage is per glyph where the glyphs can be placed, so a black box over a value inside a sentence (the usual shape of a failed redaction) is found, and the message names exactly the covered passages with a bbox for each; elsewhere it falls back to whole-span coverage of at least 90%. The rest of the line is visible text and reads normally — only the named passages are hidden. This is an error-level trust signal and can indicate an ineffective visual-only redaction: a reader of the page sees a black box where `pages[].text` has the passage, so do not present the passage as visible content; whether to disclose it is the agent's call. The detector requires positive rectangular path geometry encoded in at most 16 path numbers; complex paths (including even-odd frames with holes), annotation appearance operators, transparent fills, active clips or soft masks, transparency-group fills, optional-content fills, and non-normal blend-mode fills are excluded. Adjacent text-show runs may align to one extracted span only by deterministic ordered concatenation; when extraction deduplicates identical text paints, the last ordered exact match determines whether the fill is actually later. Collection and alignment fail closed above 4,096 candidate spans, text runs, or candidate fills; 65,536 span, raw-run, or NFKC-normalized UTF-16 code units; a shared budget of 1,000,000 run/code-unit comparison steps; or 250,000 span/fill coverage checks per page. Treat the listed passages and matching native search hits as exposed hidden content; `--render-region` on a listed bbox shows what a reader sees there. Detection is suppressed on raster-backed OCR text layers. No `--geometry`, `--vector-boxes`, or `--annotations` flag is required.
- **`text_matches_background`** (always-on operator-list signal) — native text is filled in the colour of what is painted behind it (white on a white page, or on a white or same-coloured box), so a reader sees blank space where `pages[].text` has words; the message names the passages with a bbox for each. This is a `warning`, not an error: the text is really in the file, and the commonest cause is invisible production metadata (printer slugs, job IDs, the GPO "VerDate … Jkt …" line on Federal Register pages), though a clause hidden by recolouring it, a redaction done by changing the text colour, or keyword stuffing look the same. Either way the passages are not what a reader sees, so do not present them as visible content; render a listed bbox when the passage matters to the answer. It fires only when the background is provably known — an opaque device-colour rectangle or bare page — so light text over photos, gradients, rounded or other complex shapes, and pale but visible text (watermarks) stay silent; absence of the warning is not proof that every glyph is visible. Suppressed on raster-backed OCR text layers.
- **`dense_vector_graphics`** (always-on `vectorCount` signal) — fires on pages dominated by meaningful vector drawing operations. Text-dominant pages whose many vectors are only small scattered decorations are suppressed. Common firing cases: forms, checkboxes, table rules, chart paths, and diagrams whose visible structure is not represented by native text.
- **`text_row_vector_bars`** (needs `--layout`; uses the internal fill colours of vector paths) — filled, non-white bars only: stroked form boxes, rules and underlines thinner than 3 pt, bars holding text (shaded rows, labelled boxes), bars of mixed heights or scattered down the page (flowchart arrows), and bars past all text (margin decoration) do not count; not emitted when `dense_vector_graphics` fired. Side lines, arrows between text boxes and vertical column charts are not covered.
- **`vector_graphics_no_native_text`** (always-on `vectorCount` signal) — fires when a nonblank vector-only page has no native text. Common cases: symbols, diagrams, or path-drawn labels that render visibly but do not appear in `pages[].text`; inspect `--render`, `--vector-boxes`, or `--visual-regions`.
- **`tabular_numeric_layout`** (needs `--layout`) — fires when many short numeric lines form multiple aligned columns with shared row positions. Common cases: financial statements and dense numeric tables whose row/column relationships are visually obvious but can be flattened in plain native text. Irregular financial tables can still surface when labelled rows have recurring numeric columns; chart-axis tick labels and irregular chart data-label rows are suppressed.
- **`vector_chart_labels`** (needs `--layout`; Markdown always has it) — fires when a cluster of vector paths with bars (at least three text-free marks of one width standing side by side on one baseline with different lengths, or the horizontal equivalent) holds labels that are mostly short and at least 30% numeric, including a word, and no layout table already covers it. Line charts and diagrams without bars do not fire it. The labels are read as one group (bar by bar over vertical bars, otherwise row by row) next to the caption, but their order does not pair a value with its bar, series or category; render the named region before quoting or comparing values. Gridded or ruled tables (numbers inside text-bearing cells) do not fire.
- **`layout_table_uncertain`** (needs `--layout`; Markdown computes layout internally, so it also appears there without the flag) — fires for one `layout.tables[]` entry when its geometry is self-contradictory: (1) a horizontal text line containing a digit has its centre strictly inside the table bbox and at or below the top of the first body row (a row with a value next to another cell), yet no single cell holds at least half its area — a dropped row or value; when its centre is above the first body row's top only a bare value counts, because unclaimed text there is header context; vertical (stacked CJK) lines are never counted; (2) one row has two value cells (numbers or dash placeholders) assigned to the same `column`; (3) two neighbouring columns are each filled by at least two body rows but never by the same row — one visual column split in two, or two stacked tables with different grids read as one, so a value's column depends on which row it is in; or (4) a row's label wraps over lines above the line that carries its values, the row above has values and ends its label in a full-width line in the same column, and those lines sit no clearly closer to their own values than to the row above — nothing in the spacing says whether they finish the label above or start this one (they are kept with this row, as statements set them). The message lists which of these fired and the table bbox; render that region and read the values from the image before trusting the table. A table with empty cells, merged values, or grouped headers is not flagged by itself, and unclaimed text-only lines (notes, captions, wrapped prose) are not counted.
- **`dot_leader_noise`** (native text/layout signals) — fires when many standalone dotted leader/noise lines are extracted as separate text. Common cases: table-of-contents leaders, table leaders, map stipple, and decorative dot patterns that visually connect labels or represent texture but can appear as noisy dot paragraphs in plain native text.
- **`tiny_native_text_noise`** (needs `--layout` or `--geometry`) — fires when long native text runs are set at extremely small sizes, such as hidden producer links. Treat matching `pages[].text`, links, and search hits as possibly not human-visible until checked against `--render`.
- **`duplicate_text_layer`** (internal spans; no flag required) — fires when native text contains a hidden near-duplicate layer of visible text at a consistent scaled/shifted position. It can co-occur with `off_page` or `text_overlap` because those are separate geometry symptoms; prefer the render or OCR when exact visible text matters.
- **`raster_backed_text_layer`** (internal image-box pass; no flag required) — native text appears to be an OCR/text layer over a full-page raster scan, including sparse OCR layers on scanned covers with minor decorative vector marks. Treat the text as potentially useful but error-prone: recognition can be wrong, exact native `--search` can miss visible words, and `spans` / `layout.blocks` may not line up exactly with the pixels a human sees. Re-run with `--ocr` when wording or search recall matters.
- **`raster_text_layer_symbol_noise`** (on raster-backed text layers) — the native text is dominated by printable punctuation/symbol noise (for example old scan OCR title pages full of `^`, `_`, and stray marks). Treat native text as especially suspect even if `quality.nativeTextStatus` is still `ok`.
- **`raster_text_layer_word_fragmentation`** (on raster-backed text layers) — many Latin words have split into isolated letter fragments (for example `r e p o r t`). Treat exact wording and native search misses as suspect; compare a render or rerun with `--ocr`.
- **`raster_image_no_native_text`** (internal image-box pass; no flag required) — a raster image dominates the page but native text is empty. Human-visible text inside the image will not appear in `pages[].text`; compare the render or OCR when exact text matters. On empty-native-text pages this warning subsumes `large_raster_low_text_overlap`.
- **`large_raster_low_text_overlap`** (internal image pass; stronger with `--image-boxes` + `--layout`/`--geometry`) — appears on empty/sparse-text visual pages when the internal image pass sees a large raster. With `--image-boxes` plus `--layout` or `--geometry`, it compares native text bboxes against raster regions and includes `imageBoxIndex` for pinpoint follow-up. Not emitted on empty-native-text pages where `raster_image_no_native_text` already fired. Treat it as "labels, chart text, map text, or screenshot text inside this image may need `--render` / `--render-region` / OCR."
- **`ocr_low_confidence`** (needs `--ocr`) — OCR confidence below 0.5 while native extraction is empty, sparse, glyph-corrupted, or riding on a raster-backed text layer. Treat OCR text as tentative; compare with `--render`, adjust `--ocr-lang`, or crop/retry before trusting form labels or small print. See `pdfvision docs ocr`.
- **`ocr_native_text_mismatch`** (needs `--ocr`) — OCR confidence is high, native extraction is otherwise `ok`, and OCR strongly disagrees with native text. Common cases: a custom font renders a word correctly while native text extracts as printable glyph substitutions, or a raster-backed scan has high-confidence OCR words whose nearest native tokens are wrong. Compare against `--render`; for raster-backed pages, prefer OCR-backed search hits over native search misses. See `pdfvision docs ocr`.
- **`ocr_native_spacing_loss`** (needs `--ocr`) — OCR ran on a raster-backed text layer, OCR confidence is high, OCR and native text contain comparable characters, but native text has lost many word boundaries (`Ourwebsite` / `valuableresourcefor`) while OCR restores normal spacing. Compare `ocr.text` with the render when exact wording matters. See `pdfvision docs ocr`.
- **`annotation_text_missing_from_native`** (internal annotation pass; no flag required) — visible FreeText annotation contents are not represented in `pages[].text`, even without `--annotations`. Treat native text as incomplete; read `pages[].annotations`, use `--search`, or render the annotation bbox when exact visible text matters.
- **`optional_content_text_may_include_hidden_layers`** (always-on signal) — the page text stream contains optional-content marked text and the PDF has at least one layer hidden in the default viewer state. pdf.js text extraction can include text from layers a human does not initially see; inspect `--layers` and compare against `--render` before trusting `pages[].text` as the visible text.
- **`reading_order_divergence`** (needs `--layout`) — a heading that leads the visual reading order only appears in the back half of the native text stream (magazine-style frame layouts emitted out of order — the page title buried mid-`text`), a slide-style visually-first title/header is drawn last and appears at the end of native text, a late bottom note or right sidebar appears at the start of native text, reconstructed layout lines inside one block are emitted out of order, compact math text extracts out of visual order, or `--form-fields` exposes form labels whose native text order differs from the visible row order. Prefer `layout.blocks` order over `pages[].text` when sequence matters — that is the remedy the message carries in JSON, XML, and TOON. Markdown (and therefore the MCP tools) already switches to the layout-rebuilt body on these pages, so there the message says so instead: the divergence is real, the text you are holding is already the visual order, and `--render-region` / `render_pdf` is the confirmation step when sequence is critical. The exception is a message that says `the layout-rebuilt order is unreliable here too`: side-by-side blocks (a sidebar beside the body, two columns sharing baselines) were read line by line or run together, so neither `layout.blocks` nor the Markdown body is in reading order — on every surface, render the page and read it from the image. Absence of that clause is not proof the rebuilt order is right; it only means neither defect was seen.
- **`rotated_page_read_unrotated`** (always-on; rotated pages only) — fires when a page has a `/Rotate` and most of its native characters have an upright left-to-right baseline as stored but not after the rotation. Such a page is read and rendered in its stored orientation, so its geometry and PNG are unrotated while `rotation` still reports the page dictionary value. A rotated page with no native text, or whose text is upright after rotation, never fires it and is read in the displayed frame.
- **`xfa_form`, severity `error`** (always-on document signal, attached to the first extracted page) — the document declares XFA **and** the pages that came back are confirmed to be the dynamic-XFA viewer placeholder, nothing else. The real form content lives in an XML stream that standard extraction never sees; the page tree holds one generated "Please wait... upgrade Adobe Reader" page, which is why the reported page count can collapse to one. Never answer from that text, and do not read a search miss over it as absence — a hit and a miss are equally uninformative. Rendering does not help here: the render is the placeholder. Report that the document is an XFA form whose content pdfvision does not extract, and suggest opening it in Adobe Acrobat/Reader. `search_pdf` says the same thing in its response, on zero hits as well as hits, and for every page in the selection. Severity is `error` because what came back is not data about this file.
- **`xfa_form`, severity `warning`** (same signal, unconfirmed) — XFA is declared, nothing extracted looks like content, and yet nothing establishes the placeholder either: no marker matched, and the document has no static field layer to vouch for it. This is deliberately not a verdict. Render or OCR the pages — if they show only a "Please wait" notice, treat the document as the `error` case above; if they show the form, the pages are real and the missing text is an ordinary extraction problem (see `raster_image_no_native_text`, `glyph_garbage_text`). A search miss here is not evidence of absence either. JSON/TOON/library use top-level `xfa: true`; XML uses `<document xfa="true">`.
- **`xfa_fields_only`** (always-on document signal, attached to the first extracted page) — the document declares XFA, its AcroForm field layer is real and extracted, and the pages alongside it carry nothing of their own: the "Please wait..." placeholder, or no text at all. Both halves are true at once and neither can stand in for the other, which is why this is its own code rather than a severity of `xfa_form` — the action is neither "go to Acrobat" nor "read the pages". Answer from `formFields` and from field-source search hits, which are real; do not quote the page text or read a miss over it as absence; and report that anything outside the fields lives in the XFA layer and needs Adobe Acrobat/Reader. `search_pdf` says the same in its response.
- **`xfa_static_content`** (always-on document signal, attached to the first extracted page) — the document declares XFA **and** the static layer is the real form: the hybrid AcroForm+XFA shape used by IRS forms and most fillable government PDFs, where the page tree carries the full text and the widget fields and the XFA layer duplicates them. Extraction here is as good as on any other PDF, so read the text, fields, and search hits normally. It also covers the XFA-declaring file whose pages are a scan or a drawing rather than a form: what it asserts is only that the pages are the document's own, not that their text extracted well — the per-page warnings and `quality` answer that as usual. The one thing this code marks is the residue: values that exist only in the XFA layer — some dynamically added rows or subforms — are not extracted, so treat a *specific expected field* that is genuinely missing as possibly XFA-only rather than as evidence the form is blank. Do not escalate to Acrobat on this code alone. JSON/TOON/library use top-level `xfa: true`; XML uses `<document xfa="true">`.

How the three are told apart, in order. The inputs are `IsXFAPresent` and `IsAcroFormPresent` from pdf.js plus what the extracted pages hold.

1. **Any extracted page carries content of its own → `xfa_static_content`.** Content means more than a trace of native text, or images, or vector drawing, or recovered OCR text — a scanned page counts, because a render or OCR reads it and sending the caller to Acrobat would be wrong. Pages matching the placeholder markers are excluded from this test first, so a rule or logo on the generated page cannot promote it. This is the only branch that vouches for the page text, and it runs first for that reason.
2. **`IsAcroFormPresent` is true → `xfa_fields_only`.** A non-empty, non-signature `/Fields` array means the form can be read and filled without an XFA-aware viewer, so the Acrobat-only verdict is ruled out — but it says nothing about pages that produced nothing, so the code claims the field layer and not the text. This is a document-level fact, so a narrow `pages` selection cannot flip it.
3. **A placeholder marker matched → `xfa_form` (`error`).** The markers are the locale-independent `adobe.com/go/reader_download` and `adobe.com/go/acrreader` links and the English boilerplate sentences, on a page under 2,000 characters.
4. **Otherwise → `xfa_form` (`warning`).** Nothing was extracted and nothing confirms why.
